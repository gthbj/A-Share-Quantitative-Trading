## 2. 背景与动机

通读项目后发现以下 4 处 bug 与潜在静默失败：

### Bug A：`metrics.calculate_metrics` 的 `fills` 参数永远收不到值

`run_backtest.py` 第 330 行调用 `calculate_metrics(nav_df, engine.benchmark_df, frequency=frequency)`，未传 `fills`。
导致 `MetricsResult.total_trades / win_rate / profit_loss_ratio` **永远为 0**。
HTML 报告和 summary.md 中"交易统计"现在虽然手工实现了买/卖笔数，但 metrics 本身的字段是死的。

### Bug B：`Context.get_price` fallback 路径对分钟级回测窗口估算严重不足

`base_strategy.py:84-96`：

```python
end = datetime.strptime(date_str, "%Y%m%d")
start = end - timedelta(days=int(count * 1.5))
df = self.data_source.get_bars(code, start.strftime("%Y%m%d"), date_str, period=self.frequency)
```

- 15min 频率下 `count=20` 需要约 1.5 天数据（一天 16 根 15min bar），但代码估算的 `timedelta(days=30)` 是 30 天。等等——`int(20 * 1.5) = 30`，方向是过多而非过少，看起来无害。但反过来，对于 daily 频率 `count=20`，估算 30 天可能跨过较多非交易日，**实际只能拿到约 21-22 个交易日**，刚好够；如果用户传 `count=200`，估算 300 天，跨越约 200 个交易日，刚好够。
- 真正的问题：**分钟级时 `count=20` 估算 30 天 → 拿到约 30天 × 16 bar = 480 根 bar，远超需要**。会导致缓存/SQL 数据量爆炸（如 480 根 15min 数据需要拉取数月分区）。

虽然生产路径走 `all_bars`，但 fallback 路径单元测试或独立调用时会拉太多数据。

### Bug C：`Order.__post_init__` 静默截断不足 100 股的订单

`engine/trade_engine.py:37-41`：

```python
def __post_init__(self):
    if self.qty % 100 != 0:
        self.qty = (self.qty // 100) * 100
```

`order(code, 50)` → `qty=0`，订单**静默丢失**，无日志/无 warning。策略调试时极难发现。

### Bug D：`Context.order_target_percent` / `order_target_value` 只打 warning

`base_strategy.py:56-65` 当前实现：

```python
def order_target_percent(self, code: str, percent: float) -> None:
    logger.warning("...")
    # 暂不实现完整逻辑，防止 lookahead bias
```

策略调用后什么也不发生，但用户可能以为已下单。应改为抛 `NotImplementedError`，让错误**立刻可见**。

### Bug E：未使用的 `import copy`

`engine/trade_engine.py:5` 和 `engine/backtest.py:8` 各有一个 `import copy`，全文未使用。

不修复的后果：
- A：交易统计指标在 metrics 层永远为零；如果未来某天有报告新增字段引用它，会出错
- B：fallback 路径拉数据失控，浪费 MaxCompute 计费
- C：策略小量下单代码全部"静默成功"，bug 极难定位
- D：策略升级时误用 order_target_percent，**资金完全没动但策略以为已下单**，回测结果灾难
- E：代码混乱

## 5. 需求详情

### 5.1 功能目标

| 子项 | 内容 |
|------|------|
| **A.** 接通 metrics.fills | 在 `run_backtest.py` 中把 `engine.records` 里所有 `Fill` 收集起来，传入 `calculate_metrics(... fills=all_fills)` |
| **A.（续）** 实现 win_rate / profit_loss_ratio | 用 FIFO 配对：按时间顺序对每只股票的买/卖配对，盈利配对数 / 总配对数 = win_rate；总盈利 / 总亏损绝对值 = profit_loss_ratio |
| **B.** 修正 get_price fallback | 按 frequency 调整估算系数：daily 用 `days = count * 1.6`（兼容节假日），分钟级用 `days = max(2, ceil(count / bars_per_day) + 2)` |
| **C.** Order 不足 100 股提示 | 不足 100 股时打印 warning（保留向下取整行为，不抛错，避免破坏已工作的策略）|
| **D.** order_target_* 抛错 | 改为 `raise NotImplementedError("order_target_percent 尚未实现，请手动计算目标数量后调用 context.order()")` |
| **E.** 移除未用 import | 删除 `engine/trade_engine.py:5` 与 `engine/backtest.py:8` 的 `import copy` |

### 5.2 交互流程

A 项 metrics.fills 配对逻辑示例：

```
某 code 的 fills 时间序列:
  buy 100 @10.0
  buy 100 @11.0
  sell 100 @12.0
  sell 100 @11.5

FIFO 配对：
  trade1 = sell(@12.0, 100) - buy(@10.0, 100) = +200 (盈利)
  trade2 = sell(@11.5, 100) - buy(@11.0, 100) = +50  (盈利)

→ win_rate = 2/2 = 100%
→ profit_loss_ratio = 250 / 0 = inf（无亏损时返回 None 或 inf 字符串）
```

未配对的剩余仓位（最后还持有的）忽略。

## 10. 备注

- **风险点 1**：FIFO 盈亏配对若实现错误会影响 win_rate / pl_ratio 的可信度。配对算法应单独编单元测试（见 PRD_20260520_07）。
- **风险点 2**：B 项 fallback 修复对生产路径无影响，但应在 base_strategy 中添加注释说明"生产路径走 all_bars 内存"。
- **风险点 3**：D 项改抛错可能让已经在使用 order_target_percent 的用户策略立刻失败。当前 codebase 内**没有**任何策略使用这两个方法（grep 确认），故不影响。
- 不存在 Lookahead Bias，所有改动均在 metrics 后处理与策略接口层。
