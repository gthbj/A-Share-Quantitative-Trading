## 2. 背景与动机

PRD_20260520_06 已实现 LIMIT / STOP 撮合规则（`_resolve_trigger_and_price`），但订单生命周期上有一个被 PRD_06 备注 §10「风险 3」明确标记为"待补"的缺陷：

> 风险 3：未实现订单 TTL（过期）与取消接口。挂单永远有效直到成交或回测结束，可能与真实长效订单不符。

实际行为比备注描述更糟。引擎的当前路径是：

```python
# engine/backtest.py L168
orders = context.pop_orders()  # 一次性取走 + 清空
# ...
fills = self.trade_engine.execute_orders(orders, ...)  # 逐单试一次
# 未触发的 LIMIT/STOP 单：fill 为 None，但**丢弃**，下一根 bar 再也不会重试
```

`context.pop_orders()` 会清空 `_orders`，未触发的 LIMIT / STOP 在该轮失效，**等价于"挂单当根 bar 不成交就消失"**。这与策略层对 `limit_order` / `stop_order` 的自然预期（挂单留到成交或过期）相悖。

**不修复的后果**：
- 任何"在固定价位等成交"的策略行为不可建模（如 5% 止盈卖单挂着、突破止损单挂着）
- 策略只能在每根 bar 重新下挂单，逻辑混乱且与真实交易不符
- 策略无法主动撤单——某些场景（如行情突变需要换价）做不到

## 3. 影响模块声明

- **`engine`**（`trade_engine.py` Order 字段 + 挂单池；`backtest.py` 主循环引入"挂单池扫描"）
- **`strategy`**（`base_strategy.py::Context` 的 `limit_order` / `stop_order` 接收新参数；新增 `cancel_order`）
- **不影响**：`paper_trader.py`（虚拟盘的对应集成放到后续 PRD，等 PRD_09 落地后再做）

**回测可复现性**：
- 现有 4 个策略均使用 `context.order()`（MARKET 分支），其完整行为不变
- 现有用 `limit_order` / `stop_order` 但未指定 `expire_date` 的策略：行为从"当根 bar 不成交即丢"变为"挂到回测结束都不丢"。该变更**修复了已知 bug，但会改变 nav**。当前仓库内**没有任何策略**调用这两个接口，故无回测可复现性影响。

## 5. 需求详情

### 5.1 功能目标

**A. `Order` 数据类新增三个字段**

```python
@dataclass
class Order:
    code: str
    side: OrderSide
    qty: int
    order_type: OrderType = OrderType.MARKET
    price: Optional[float] = None
    stop_price: Optional[float] = None
    # —— 新增 ——
    time_in_force: str = "DAY"          # "DAY" 或 "GTC"
    expire_date: Optional[str] = None    # YYYYMMDD；None 表示无指定日期上限
    order_id: str = ""                   # 系统自动生成
```

字段语义：
- `time_in_force == "DAY"`：当个交易日内有效，到该日最后一根 bar（含）撮合后仍未成交则失效。
- `time_in_force == "GTC"`：到 `expire_date`（含）当日撮合后仍未成交则失效。`expire_date is None` 表示无截止日，直到回测结束都挂着。
- `order_id`：自动以 `uuid4().hex[:12]` 生成；MARKET 单也会生成（便于将来扩展，但 MARKET 不进池）。

**B. `TradeEngine` 维护"未成交挂单池"**

新增成员：

```python
self.pending_orders: Dict[str, Order] = {}   # order_id -> Order
```

新增方法：

```python
def add_pending(self, order: Order) -> None:
    """将 LIMIT/STOP 未触发单加入池。MARKET 拒绝入池。"""

def cancel(self, order_id: str) -> bool:
    """从池中移除。命中返回 True，否则 False。"""

def sweep_pending(
    self,
    portfolio: Portfolio,
    bar_data: Dict[str, pd.Series],
    current_date: str,
    is_last_bar_of_day: bool,
) -> List[Fill]:
    """每根 bar 调用：
    1) 遍历池子，对每个挂单调 _try_fill
       - 成交：fill 收集到返回值；从池中移除
       - 未成交：继续判断是否过期；过期则从池中移除（不成交、不报错）
    2) 过期判定：
       - DAY：is_last_bar_of_day=True 且当根仍未触发 → 过期移除
       - GTC：current_date > expire_date（按字符串比较 YYYYMMDD）→ 过期移除
    """
```

**修改 `execute_orders` 语义**：

```python
def execute_orders(
    self,
    orders: List[Order],
    portfolio: Portfolio,
    bar_data: Dict[str, pd.Series],
    current_date: str,
) -> List[Fill]:
    """执行本根 bar 的新订单：
       - MARKET：一次性尝试，不进池
       - LIMIT/STOP：尝试一次，未触发则入池
       与 sweep_pending 互补使用。回测主循环顺序：
         step1: sweep_pending（处理前期挂单 + 过期清理）
         step2: execute_orders（处理本根 bar 新订单 + 未触发的进池）
    """
```

**C. `Context` 接口扩展**

```python
def limit_order(
    self, code: str, amount: int, price: float,
    time_in_force: str = "DAY",
    expire_date: Optional[str] = None,
) -> str:
    """挂限价单。返回 order_id。"""

def stop_order(
    self, code: str, amount: int, stop_price: float,
    time_in_force: str = "DAY",
    expire_date: Optional[str] = None,
) -> str:
    """挂止损单。返回 order_id。"""

def cancel_order(self, order_id: str) -> bool:
    """取消挂单。先在本根 bar 未发出的 _orders 里找，再委托给引擎的 pending_orders。
    命中返回 True，否则 False。
    """
```

约束：
- `time_in_force` ∈ {"DAY", "GTC"}，其他值抛 `ValueError`
- `expire_date` 仅在 `time_in_force == "GTC"` 时有意义；若 DAY 单传了 `expire_date` 抛 `ValueError`（防止用户混淆）
- 既有的 `order()`（MARKET）签名不变；MARKET 单的 `time_in_force` 隐式为"立即"，不进池

**D. `Context.cancel_order` 与引擎的协作**

Context 与 TradeEngine 通过 `_engine_ref`（弱引用或显式注入）解耦。具体方案：

- `BacktestEngine._run_daily / _run_intraday` 构造 Context 时注入 `context._cancel_callback = self.trade_engine.cancel`
- Context 的 `cancel_order` 先在自己的 `_orders`（本根 bar 还没下发的新单）里搜，命中即移除；否则调 `_cancel_callback`

**E. 回测主循环改造**

`engine/backtest.py::_run_daily`：

```python
for i, date_obj in enumerate(trading_days):
    # ... 现有 today_bars / prev_close / before_trading_start 部分不动

    # —— 新增 step A：扫前期挂单 ——
    is_last_bar_of_day = True   # 日线：每天就一根 bar
    sweep_fills = trade_engine.sweep_pending(
        portfolio, today_bars, date_str, is_last_bar_of_day
    )

    # —— 现有 step B：执行 next_open 新订单 + 止损单 ——
    orders = context.pop_orders()
    orders.extend(stop_loss_orders)
    # ... 资金预留逻辑不动 ...
    new_fills = trade_engine.execute_orders(orders, portfolio, today_bars, date_str)

    # ... handle_data / after_trading_end / 止损检查 / NAV 记录 ...
```

`_run_intraday` 同构改造，但 `is_last_bar_of_day` 需要判断当前 bar 是不是当日最后一根（已存在的 `_iter_minute_bars` 内有日期切换检测，沿用其语义）。

## 10. 备注

- **风险 1：order_id 持久化**。`Order` 加 `order_id` 后，如果未来要让虚拟盘跨日持久化挂单，order_id 应一并写入 state.json。本 PRD 不涉及虚拟盘，留作后续 PRD 处理。
- **风险 2：是否引入 Lookahead Bias**。`sweep_pending` 用当前 bar 的 high/low 判触发，与 `_try_fill` 已有逻辑一致，**不引入未来函数**。过期判定基于 `current_date`（按字符串比较），不依赖未来信息。
- **风险 3：分钟级回测的 DAY 单**。"is_last_bar_of_day" 需要回测主循环可靠地识别当日最后一根 bar。`_run_intraday` 的现有日期分组逻辑已足够（详见 backtest.py 内 `current_day` 切换处）。
- **风险 4：挂单池资金占用**。本 PRD **不预先冻结挂单所需资金**——LIMIT 买单触发瞬间才检查 `available_cash`。这与 PRD_06 既有语义一致，避免长期 GTC 单锁死大量资金。代价是触发瞬间可能因资金不足而 `_try_fill` 返回 None（订单从池中清除？还是保留？）——**本 PRD 明确为"清除并 WARNING 日志"**，等同于"挂单已发但成交失败"。
- **风险 5：DAY 单在分钟级回测的"日终"语义**。若一根 bar 的日期与下一根 bar 不同（跨日），则当前 bar 视为日终。最后一个交易日的最后一根 bar 也视为日终。
- 现有 `chinese_calendar` 范围（覆盖至 2026 年）够用，本 PRD 不依赖未来年份的交易日历准确性。
- 与 TBD-1（虚拟盘策略循环）**完全解耦**：本 PRD 不动 `paper_trader.py`，等 PRD_09 + TBD-1 落地后再开 PRD 把挂单池接入虚拟盘。
