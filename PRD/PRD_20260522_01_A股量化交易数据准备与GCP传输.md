# A股量化交易 BigQuery 数据准备 PRD

## 1. 背景与目标

项目目标是建设一个面向 A 股日线级别量化研究、回测、机器学习训练和每日收盘后生成 T+1 开盘交易信号的数据底座。

当前本地非分钟数据约 7.3GB，约 1.88 万个文件，主要为 CSV、ZIP、XLSX。D 盘剩余约 158GB，物理内存约 31.8GB，当前空闲约 16.1GB。数据量适合本地先标准化、去重、转 Parquet 后上传 BigQuery，但不建议一次性全量加载进内存，应采用流式、分块、按文件/按月份处理。

## 3. 数据分层与存储设计

### 3.1 原始数据保留策略

原始文件建议长期保留在 GCS，而不是长期完整保留在 BigQuery。

推荐分层：

| 层 | 建议位置 | 作用 |
| --- | --- | --- |
| 原始文件层 | GCS，例如 `gs://ashare-data/raw/...` | 保存原始 CSV/ZIP/XLSX，作为可追溯、可重跑的数据源 |
| 标准化文件层 | GCS，例如 `gs://ashare-data/standardized/...` | 保存本地或云端标准化后的 Parquet 文件，供 BigQuery 装载 |
| 原始解析/临时层 | BigQuery `ashare_raw` | 保存 manifest、staging 表、解析错误、抽样审计数据，可设置 30-90 天过期 |
| 标准化明细层 | BigQuery `ashare_core` | 保存清洗、标准化、去重后的长期核心数据 |
| 研究特征层 | BigQuery `ashare_mart` | 保存面向策略、机器学习、回测的宽表和结果表 |

不建议 BigQuery 长期保存完整 raw 明细，原因：

- raw 字段不统一，直接分析价值低。
- BigQuery 长期存储 raw 会增加成本。
- 原始文件格式复杂，GCS 更适合保存 ZIP、CSV、XLSX 等对象。
- 只要保留 GCS 原始文件、处理脚本、manifest 和版本信息，就可以重跑生成 core/mart。

### 3.2 BigQuery Dataset 设计

建议分 3 个 BigQuery dataset：

| Dataset | 用途 |
| --- | --- |
| `ashare_raw` | 原始解析/临时层。保存上传 manifest、staging 表、解析错误、抽样审计数据，不建议长期保存完整 raw 明细。 |
| `ashare_core` | 标准化明细层。统一字段名、代码、日期、类型、去重后的核心事实表和维度表。研究和回测主要读这一层。 |
| `ashare_mart` | 研究宽表/特征层。面向策略、机器学习、回测构建特征快照，例如 `equity_features_1d`、`universe_1d`、`ml_labels_1d`。 |

不建议按股票、基金、财务拆太多 dataset。BigQuery 中 dataset 更适合表达权限、生命周期和层级，表才表达业务域。

### 3.3 `ashare_raw` 表设计

| 表名 | 作用 | 包含数据 |
| --- | --- | --- |
| `ingestion_manifest` | 断点续传、文件去重、处理状态追踪 | 源文件路径、ZIP 内文件名、文件大小、修改时间、文件 hash、目标表、分区月份、行数、处理状态、错误信息 |
| `ingestion_errors` | 记录解析失败、字段异常、代码无法识别等问题 | 文件路径、错误类型、错误字段、原始值、错误信息、发生时间 |
| `stg_*` | 临时上传表，用于 `MERGE` 到 core 表 | 每个目标表上传前的临时数据，保留时间较短，可按批次或表名拆分 |

`ashare_raw` 不作为长期事实明细层。完整原始文件以 GCS 为准。

### 3.4 GCS 原始数据存储成本估算

当前纳入范围的非分钟原始数据约 `7,843,951,876` 字节，约 `7.31 GiB`。以下只估算 GCS 原始文件存储，不包含 BigQuery 存储、BigQuery 查询、跨区域读取、长期每日增量增长。

按当前规模，单区域 bucket 的月存储费很低：

| GCS 存储类型 | 适用场景 | 估算月存储费 |
| --- | --- | --- |
| Standard | 会经常读取、重跑、调试 | 约 `$0.15/月` |
| Nearline | 平均每月不到 1 次读取 | 约 `$0.07/月` |
| Coldline | 平均每季度不到 1 次读取 | 约 `$0.03/月` |
| Archive | 长期归档，基本不读 | 约 `$0.01/月` |

如果使用 multi-region，月存储费大致为：

| GCS 存储类型 | 估算月存储费 |
| --- | --- |
| Standard | 约 `$0.19/月` |
| Nearline | 约 `$0.11/月` |
| Coldline | 约 `$0.06/月` |
| Archive | 约 `$0.02/月` |

容易忽略的费用：

- 上传约 1.88 万个对象时会产生 Class A 操作费，单区域 Standard 约 `$0.09` 一次性级别，multi-region 约 `$0.19` 一次性级别。
- Nearline、Coldline、Archive 读取时有 retrieval fee；如果把当前 7.31 GiB 全量读一遍，Nearline 约 `$0.07`，Coldline 约 `$0.15`，Archive 约 `$0.37`。
- Nearline、Coldline、Archive 有最短存储期，分别约 30/90/365 天；提前删除或改存储类型可能产生早删费用。
- dual-region 或 multi-region 写入可能有 inter-region replication fee。以亚洲 multi-region 为例，当前 7.31 GiB 首次写入约 `$0.58` 级别。

建议：

- 第一阶段用单区域 Standard，位置尽量和 BigQuery dataset 放在同一区域，便于装载和重跑。
- 原始文件稳定后，可以用 lifecycle rule 将较旧对象转为 Nearline 或 Coldline。
- 暂不建议一开始使用 Archive，因为后续还会反复重跑清洗逻辑。

## 4. 统一规范

### 4.1 日期字段

所有日期字段统一：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `date` | `DATE` | 交易日期 |
| `report_period` | `DATE` | 财报报告期 |
| `announcement_date` | `DATE` | 公告日期 |
| `actual_announcement_date` | `DATE` | 实际公告日期 |
| `partition_month` | `INT64` | 年月分区辅助字段，格式如 `202505` |

### 4.2 证券代码

所有证券代码统一：

| 类型 | 标准格式示例 |
| --- | --- |
| 股票 | `000001.SZ`、`600000.SH`、`430xxx.BJ` |
| 基金 | `159001.SZ`、`510300.SH` |
| 指数 | `000001.SH`、`399001.SZ`、`000300.CSI` |
| 板块 | 保留来源后缀，例如 `BK0145.DC` |

不再使用 `sh000001`、`sz000001`、裸代码 `000001` 作为主键字段。源代码保留在 `source_code`，标准代码使用 `security_code`、`fund_code`、`index_code`、`board_code`。

### 4.3 字段命名

字段命名统一使用英文 snake_case。不同表中相同含义字段必须同名：

- `open`
- `high`
- `low`
- `close`
- `volume`
- `amount`
- `pct_change`
- `change`
- `turnover_rate`
- `amplitude`

数值字段统一使用 `NUMERIC` 或 `FLOAT64`。金额、价格、比例建议用 `NUMERIC`；机器学习特征层可转 `FLOAT64`。

### 4.4 表命名规范

业界没有唯一强制标准，但量化交易和行情数据系统里通常会区分：

- `kline` / `bar`：表示 OHLCV K线数据，包含开高低收、成交量、成交额等。
- `price`：更偏向价格快照、收盘价、估值价格、涨跌停价格等，不一定包含完整 OHLCV。
- `quote`：更偏向实时盘口、买卖档、快照行情。
- `trade`：逐笔成交。

本项目建议使用 `kline` 命名 OHLCV 行情表，而不是 `price`。原因是当前股票、基金、指数、板块行情文件都包含开高低收和成交量额，本质是 K线/bar 数据。

周期命名建议使用 `1d`、`1w`、`1mo`、`1min`、`5min`、`1h`，而不是 `daily`、`weekly`、`monthly`。这样后续扩展分钟线、小时线时更统一。

推荐格式：

```text
fact_{asset_type}_kline_{timeframe}
```

示例：

| 数据类型 | 推荐表名 |
| --- | --- |
| 股票日线 | `fact_equity_kline_1d` |
| 股票 1 分钟线 | `fact_equity_kline_1min` |
| 股票 5 分钟线 | `fact_equity_kline_5min` |
| 股票 1 小时线 | `fact_equity_kline_1h` |
| 基金日线 | `fact_fund_kline_1d` |
| 指数日线 | `fact_index_kline_1d` |
| 板块日线 | `fact_board_kline_1d` |

非 K 线类数据仍按业务语义命名，并在日频数据后加 `1d`：

| 数据类型 | 推荐表名 |
| --- | --- |
| 涨跌停价格 | `fact_limit_price_1d` |
| 停复牌状态 | `fact_suspend_1d` |
| ST 状态 | `fact_st_status_1d` |
| 板块成分 | `fact_board_component_1d` |

## 5. 分区与聚簇

所有按交易日增长的事实表：

- 分区：`date`，按 MONTH 分区。
- 聚簇：优先 `security_code` / `fund_code` / `index_code` / `board_code`，其次 `date`。

财务类表：

- 分区：`announcement_date` 或 `report_period`，按 MONTH 分区。
- 聚簇：`security_code`, `report_period`。

成分关系类表：

- 分区：`date`，按 MONTH 分区。
- 聚簇：`board_code`, `security_code`。

BigQuery 表中保留 `partition_month`，便于本地文件切片、断点续传和人工检查。

## 8. 去重与断点续传

本地处理必须生成处理清单表，可落地为 SQLite/Parquet/JSONL，也可同步到 BigQuery 的 `ashare_raw.ingestion_manifest`。

字段：

- `source_file`
- `source_entry`，ZIP 内部文件名
- `file_size`
- `file_mtime`
- `source_hash`
- `target_table`
- `partition_month`
- `row_count`
- `status`，`pending`、`processing`、`done`、`failed`
- `started_at`
- `finished_at`
- `error_message`

去重策略：

- 文件级去重：相同 `source_hash` 不重复处理。
- 记录级去重：按业务主键去重，例如 `security_code + date + adjust_type`。
- BigQuery 上传使用 staging table，再通过 `MERGE` 写入 core 表。
- 每个分区独立提交，失败后只重跑失败分区。

本地标准化输出建议为 Parquet，路径按表和年月组织，例如：

```text
D:\A Share_processed\fact_equity_kline_1d\partition_month=202505\part-0001.parquet
```

## 10. 建模与回测数据使用约束

### 10.1 避免未来函数

财务数据、公告数据、成分数据必须使用 `announcement_date` 或实际可得日期，而不是 `report_period`。训练样本按“当日收盘时已知信息”构造。

例如，某公司 2025 年年报的 `report_period = 2025-12-31`，但 `announcement_date = 2026-03-28`。在 2026-03-27 及以前的训练样本中，不能使用这份年报；只有公告日之后，才可以作为已知信息使用。

### 10.2 T+1 信号生成口径

策略在 T 日收盘后生成信号，T+1 开盘交易。T 日信号只能使用 T 日收盘时已经可获得的数据。盘后公告数据是否纳入 T 日信号，需要在每日更新流程中单独定义；保守做法是从 T+1 或下一次信号生成开始使用。

- Dataset：`ashare_raw`、`ashare_core`、`ashare_mart`。
