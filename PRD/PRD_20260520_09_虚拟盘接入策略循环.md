## 一、背景

`PaperTrader.run_once` 当前只做"持仓估值 + 状态保存"，不调用策略 `handle_data`、不撮合订单，仅仅是个**占位骨架**。需要把策略循环挂接到虚拟盘日常调度上。

---

## 二、范围

### 做：

1. 在 `BaseStrategy` 新增 `lookback_days` 属性（声明策略需要多少天历史 bar 来 warm up 指标）
2. `state.json` schema 扩展：新增 `strategy_class` / `strategy_kwargs` / `user_data` / `last_run_date` / `pending_orders` / `pending_stop_loss` 字段
3. `PaperTrader.run_once` 重构：实例化策略 → 预加载历史 → 撮合 → 调度生命周期 → 保存状态
4. 单元测试覆盖 PaperTrader 的状态加载/保存、订单延迟成交、user_data 跨日续接、重复运行拦截

### 不做：

- 实时分钟级实盘调度（当前需求只跑日线一次）
- 自动定时（cron / systemd timer 由运维层处理，不进框架）
- 实时风控（已有 stop_loss 复用即可）
- 虚拟盘绩效报告（HTML / Markdown 报告暂不生成，复用 records 后续可扩展）

## 三、核心设计

### 3.1 撮合时序：next_open（与回测对齐）

`run_once(date=T)` 处理流程：

```
1. load_state()                      → 含上次跑剩下的 pending_orders + pending_stop_loss
2. 实例化策略（用 state 里的 strategy_class + strategy_kwargs）
3. 预加载 [T - lookback_days, T] 行情，注入 context.all_bars
4. before_trading(T)                 → 解冻 T-1 买入的股票（T+1 释放）
5. 用 T 日开盘价撮合 pending_orders + pending_stop_loss（next_open 语义）
6. strategy.before_trading_start(T)
7. strategy.handle_data(T)           → 新订单进 context._orders
8. strategy.after_trading_end(T)
9. 止损检查（基于 T 日收盘价 → 加入 pending_stop_loss，下次 run_once 开盘执行）
10. save_state()                     → 含本次 handle_data 产生的订单 + 止损队列 + user_data
```

**为什么用 next_open？** 跟回测引擎 `_run_daily` 完全对齐，方便虚拟盘和回测结果对比；也避免"T 日 close 信号 → T 日 close 成交"的隐式未来函数。

### 3.2 state.json schema 扩展

```json
{
  "initial_capital": 1000000,
  "available_cash": 850000,
  "current_date": "20260520",
  "last_run_date": "20260520",
  "positions": { "510300.SH": {...} },

  "strategy_class": "strategy.double_ma.strategy.DoubleMAStrategy",
  "strategy_kwargs": {"short_window": 5, "long_window": 20, "universe": ["510300.SH"]},
  "user_data": {},
  "pending_orders": [
    {"code": "510300.SH", "side": "buy", "qty": 100, "order_type": "market",
     "price": null, "stop_price": null}
  ],
  "pending_stop_loss": {"510300.SH": 100}
}
```

向后兼容：缺失字段全部默认空值，老 state.json 仍能加载。

### 3.3 BaseStrategy.lookback_days

```python
class BaseStrategy(ABC):
    # 子类可覆盖：声明策略需要多少天历史 bar 来 warm up 指标
    # 默认 60 天对 MA20、RSI14 等常见指标足够
    lookback_days: int = 60
```

`DoubleMAStrategy` 覆盖为 `long_window + 10`（即默认 30 天，确保 MA20 有足够样本）。

### 3.4 重复运行拦截

```python
if last_run_date and last_run_date >= date:
    logger.warning(f"虚拟盘已跑过 {last_run_date}，本次请求 {date} 跳过")
    return
```

### 3.5 user_data 序列化约定

策略只能在 `context.user_data` 里塞 JSON 兼容类型（dict/list/str/int/float/bool/None）。保存时若遇到不可序列化对象，**抛 TypeError** 而不是静默丢失。

### 3.6 首次启动（state.json 不存在）

必须传入 `strategy_cls` + `strategy_kwargs`，否则抛 ValueError。已有 state.json 时这两个参数变成可选（默认沿用 state 里的）。

## 五、风险与边界

1. **`importlib` 反射重建策略**：若代码搬迁导致 `strategy_class` 模块路径失效，老 state.json 会加载失败。**约定：必要时用户手动 `--strategy <new.path>` 覆盖**。
2. **lookback_days 不够**：若策略实际需要的历史窗口比声明的大，会拿不到足够 bar，`get_price` 返回数据偏少导致策略静默不下单。**这是策略侧 bug，不在框架兜底范围**——但可以加 WARNING 提示。
3. **数据时延**：MaxCompute K 线表通常 T+1 才入库 T 日数据。`run_once` 默认取"今天或最近一个交易日"——若今日数据尚未入库，会取昨日。**符合"虚拟盘"定位**，不属于 bug。
4. **多 universe**：DoubleMA 把全部资金压在单一品种，多 universe 时先遍历到的吃光现金。这是策略本身的局限，**不在本期改造**。
