## 2. 背景

在 review `ml_rich_picker` 时发现：[walk_forward.py:188-260](../strategy/ml_rich_picker/walk_forward.py:188) 的事件特征 SQL 对不同数据源用了**不一致的时序处理**：

- KPL 表（开盘啦）显式做了 +1 交易日偏移 (`available_signal_date = MIN(td.date) WHERE td.date > k.date`)
- Money flow 和 Dragon tiger 表直接 `USING (equity_code, date)` 与 daily 对齐

这种不一致本身就说明项目内部对"什么数据可以用于 T 信号"的口径不清晰。具体表现：

| 字段 | 描述的是 T 日什么 | 物理上最早可见时刻 | 当前 SQL 处理 |
|---|---|---|---|
| `close`（收盘价）| T 日 15:00 收盘价 | T 日 15:00:01 | 直接用 T 日值 ✓ |
| `net_inflow_amount`（资金流）| T 日全天主力净流入 | **T 日 19:00** | 直接用 T 日值 ❌ |
| `dragon_tiger_net_amount`（龙虎榜）| T 日触发龙虎榜净买入 | **T 日 20:00 左右** | 直接用 T 日值 ❌ |
| `is_kpl_event`（开盘啦）| T 日 KPL 榜单 | **T+1 日 08:30** | 偏移到 T+1 ✓ |
| `pe_basic`（基本面）| 截至 T 的财务快照 | 财报公告日 ann_date | 用 `ann_date < date` 过滤 ✓ |

只要回测引擎按「T 收盘 15:00 出信号、T+1 开盘成交」的标准约定运行（`engine/backtest.py` 当前就是这个语义），那 T 日 19:00 / 20:00 的资金流和龙虎榜在 T 信号生成时**根本拿不到**，当前 SQL 等于偷看了未来 4~5 小时的数据 — 经典 look-ahead bias，**回测年化收益会虚高**。

修单条 SQL 只解决一个点；想根治这类问题，需要把"什么时候能用这条数据"这个语义**从 SQL 注释里搬进 schema**。

## 3. 设计目标

为所有事件 / 特征 / 财报类 DWS / DWD 表新增 PIT (Point-in-Time) 时序字段，让所有业务 SQL 用统一的 join 键消除歧义。

### 3.1 字段定义

| 字段 | 类型 | 含义 | 示例 |
|---|---|---|---|
| `event_date` | DATE | 业务事件发生日 | trade_date (行情)、end_date (财报报告期末) |
| `publish_date` | DATE | 信息首次公开发布日 | ann_date (公告日)、f_ann_date、actual_date |
| `available_at` | TIMESTAMP | 策略系统真正能看到的时间点（含日内时分） | "2024-01-15 19:00:00" |
| `tradable_date` | DATE | 首个允许把该数据作为信号输入的交易日 | "2024-01-16" |

### 3.2 业务 SQL 的统一形态

所有事件特征 JOIN 一律走 `tradable_date`：

```sql
-- 当前（不一致）
LEFT JOIN money    USING (equity_code, date)                       -- lookahead
LEFT JOIN dragon   USING (equity_code, date)                       -- lookahead
LEFT JOIN kpl      ON kpl.available_signal_date = d.date          -- 需要 trade_dates 子查询

-- 改造后
LEFT JOIN money  ON money.equity_code  = d.equity_code AND money.tradable_date  = d.date
LEFT JOIN dragon ON dragon.equity_code = d.equity_code AND dragon.tradable_date = d.date
LEFT JOIN kpl    ON kpl.equity_code    = d.equity_code AND kpl.tradable_date    = d.date
```

KPL 那段复杂的 `available_signal_date = MIN(td.date) WHERE td.date > k.date` correlated subquery **可以整段删除**——逻辑搬到 ETL 层算 `tradable_date` 时一次性处理。

## 4. 各表的字段映射

以「T 收盘 15:00 出信号、T+1 open 成交」为项目统一约定。

| 表 | event_date | publish_date | available_at | tradable_date |
|---|---|---|---|---|
| `dws_equity_daily_features` | T | T 15:00 | T 15:00 | **T** |
| `dwd_fact_equity_kline_1d` | T | T 15:00 | T 15:00 | **T** |
| `dwd_fact_money_flow_1d` | T (trade_date) | T 19:00 | T 19:00 | **T+1** |
| `dwd_fact_dragon_tiger_seat_1d` | T | T 20:00 | T 20:00 | **T+1** |
| `dwd_fact_kpl_board_1d` | T | T+1 08:30 | T+1 08:30 | **T+1** |
| `dws_equity_fundamental_features` | end_date（季末） | ann_date | ann_date 18:00 | **next_trading_day(ann_date)** |
| `dws_equity_event_money_flow_features_1d` | T | 取 max(组件 publish_date) | 取 max(组件 available_at) | **MAX(组件 tradable_date)** |

说明：
- 衍生宽表（如 `dws_equity_event_money_flow_features_1d`）的 `tradable_date` 应取所有上游事件源的 max（最保守口径）
- 财报的 `tradable_date = next_trading_day(ann_date)` 因为公告通常盘后发出，需要穿过节假日

## 5. 关键设计点与陷阱

### 5.1 tradable_date 不是纯数据属性，跟"信号时刻"耦合

同一份 T 日 19:00 推送的资金流：
- 项目假设「T 15:00 close 出信号」→ `tradable_date = T+1`
- 项目假设「T 20:00 盘后出信号」→ `tradable_date = T`

**红线**：项目宪法级别锁定一个信号时刻约定，所有 `tradable_date` 按该口径计算。当前项目按 `engine/backtest.py` 的实现是「T 15:00 close 信号」。

如果未来要做盘后策略，单独建一份带 `tradable_date_after_close` 字段的视图，不要改主字段的语义。

### 5.2 tradable_date 必须穿过节假日

T 是周五、money flow T 19:00 推送 → 下个交易日是周一 → `tradable_date = 周一`，**不是 `T+1 = 周六`**。

**实现要点**：ETL 层 join 一份 `dim_trade_calendar`，不能简单 `DATE_ADD(event_date, 1)`。

### 5.3 publish_date 应是"最早公开发布"而非"入仓时间"

历史数据回溯入仓时（如 2020 年的龙虎榜数据 2025 年才入仓），`publish_date` 必须填 **2020 年那条数据当年实际公开的日期**，否则历史回测会误以为整个回测期都拿不到数据。

**数据修正场景**：财报后来修正了，`ann_date` 是首次公告日还是修正日？
- 建议保留首次公告日为 `publish_date`
- 修正版另起一行（不覆盖），按 `publish_date <= signal_time` 取最新有效版本

### 5.4 盘中 vs 盘后公告的精度问题

财报公告可能上午 09:00 出（盘中可知，T 日可用）也可能 18:00 出（盘后才知，T+1 才可用）。`publish_date` 只到日级（YYYYMMDD）会丢失这个信息。

**两种处理**：
- `available_at TIMESTAMP`：精确到时分，最准确但 storage 成本高
- `publish_date DATE` + `is_published_after_close BOOL`：日级 + 标志位，足够大多数场景

当前项目里财报 SQL 已经用 `financial_announcement_date < date` （严格小于）保守处理，相当于默认所有公告都视为盘后——以这个为底线。

### 5.5 现存数据的 backfill 策略

| 表 | backfill 方式 |
|---|---|
| `dwd_fact_equity_kline_1d` / daily features | trade_date 就是 event_date，PIT 无歧义 → `event_date = tradable_date = trade_date` |
| `dwd_fact_money_flow_1d` | 没有原生 publish 时间，按经验规则 `tradable_date = next_trading_day(event_date)` |
| `dwd_fact_dragon_tiger_seat_1d` | 同上 |
| `dwd_fact_kpl_board_1d` | 同上（次日 08:30 发布，但 next_trading_day 已包含） |
| `dws_equity_fundamental_features` | 源表已有 `ann_date` / `f_ann_date` → 直接映射 + next_trading_day |

### 5.6 不同采集源的延迟差异

同一个事件，Tushare / AKShare / 东方财富 推送时间不同。`available_at` 应按"项目实际订阅的源"来定，不是理论最早可知时间。

**实现要点**：在 `data_layer` 入仓代码里硬编码每个源的发布时序常量，不要让 ETL 自行猜。

## 6. 落地步骤

### Phase 1：Schema 改造（最小集）

每张事件 / 特征 / 财报表加 2 个字段：

```sql
ALTER TABLE `data-aquarium.ashare.dws_equity_daily_features`
  ADD COLUMN event_date DATE,
  ADD COLUMN tradable_date DATE;
-- 对每张相关表重复
```

`publish_date` / `available_at` 暂不强求所有表都有——它们主要用于审计 / 调试。生产 SQL 全程走 `tradable_date`。

### Phase 2：ETL 层统一计算

在 `bigquery_pipeline` / `gcs_to_bigquery` 加共享 UDF：

```sql
CREATE OR REPLACE FUNCTION `data-aquarium.ashare.next_signal_day`(
  event_date DATE,
  published_after_close BOOL
) AS (
  CASE
    WHEN published_after_close THEN
      (SELECT MIN(c.date)
         FROM `data-aquarium.ashare.dim_trade_calendar` c
        WHERE c.date > event_date AND c.is_trading)
    ELSE
      (SELECT MIN(c.date)
         FROM `data-aquarium.ashare.dim_trade_calendar` c
        WHERE c.date >= event_date AND c.is_trading)
  END
);
```

每张表的 backfill / 增量入仓时，按下表硬编码 `published_after_close`：

| 表 | published_after_close |
|---|---|
| daily / kline | FALSE |
| money_flow | TRUE |
| dragon_tiger | TRUE |
| kpl_board | TRUE |
| fundamental | TRUE（保守）|

### Phase 3：业务层 SQL 改造

涉及文件（必改）：

- `strategy/ml_rich_picker/walk_forward.py` 的 `_load_rich_features_from_bq`
- `strategy/ml_multi_horizon_picker/walk_forward.py` 的 `_load_features_from_bq`
- 任何 `bigquery_pipeline` / `data_layer` 里 JOIN 多表的查询

改造要点：
1. 所有 LEFT JOIN 改成走 `tradable_date`
2. 删除 `kpl_mapped` / `available_signal_date` 那段 correlated subquery
3. 用 `tradable_date BETWEEN @start_date AND @end_date` 替代 `date BETWEEN ...`
4. partition 字段保持原 `date` 不变（物理 partition），逻辑 join 走 `tradable_date`

## 7. 该方案能解决什么

| 问题 | 4 字段方案能解决吗 |
|---|---|
| money / dragon 用 T-日值导致 lookahead | ✅ 完全解决 |
| KPL 那段复杂 correlated subquery SQL | ✅ 简化成普通 JOIN |
| 财报盘中 / 盘后公告精度 | ✅ 解决（需 `available_at` 到时分，或 `published_after_close` 标志位） |
| 跨节假日 tradable_date | ✅ 解决（ETL 层 join 交易日历） |
| 不同策略不同信号时刻 | ⚠️ 需项目级约定锁定，否则字段语义会漂移 |
| 数据修正版（财报二修）| ⚠️ 需配套约定"保留首次 + 修正版另起一行" |
| sell label 设计问题（PRD_06 §相关）| ❌ 跟 PIT 无关，是 label 业务定义问题，另立 PRD |

## 8. 不做范围

- 不改 ODS 层（raw）字段，PIT 是 DWD / DWS 层概念
- 不做实时流式 ETL 改造，仍是 T+1 批处理
- 不强求 `publish_date` / `available_at` 在所有表都精确到分钟级；优先把 `tradable_date` 填对即可
- 不解决"同一只股票 T 日多次停牌复牌"等极端边界，按交易日历能识别的口径处理

## 9. 验收标准

1. 所有 7 张事件 / 特征 / 财报表都有非 NULL 的 `event_date` 和 `tradable_date` 字段
2. `next_signal_day` UDF 在 BigQuery 可调用，对节假日 / 长假返回正确的下一交易日
3. `walk_forward.py` 的 SQL 不再包含 `available_signal_date` 子查询；JOIN 全部走 `tradable_date`
4. `tests/test_pit_contract.py` 全部通过
5. 用 git diff 对比改造前后同一段回测区间的 ml_rich_picker 训练集行数 / label 分布；偏差 > 5% 的部分要有合理解释（通常来自 lookahead 被关掉后样本减少）
6. 改造后跑一次 2020-2025 的 ml_rich_picker walk_forward + 回测，记录新旧年化收益对比；预期**年化收益会下降**（因为关掉了 lookahead）

## 10. 备注

### 10.1 与 `ml_rich_picker` 业务可信度修复（PRD_06）的关系

PRD_06 已经修了 BacktestEngine 默认 adjust、缓存 key 区分复权、stock_list as-of 等问题。本 PRD 是 PRD_06 的**深一层**——把"什么时候能用这条数据"这个口径从特定策略 SQL 里搬进通用 schema，让后续任何新策略都能直接受益。

### 10.2 推荐 review 顺序

1. 先把 PIT schema 落到 DWS / DWD（Phase 1 + 2）
2. 然后改 `ml_rich_picker` 的 SQL（Phase 3 的一部分）
3. 跑回归回测，确认年化下降在合理区间
4. 推广到 `ml_multi_horizon_picker` 和其他读 DWS 表的策略

### 10.3 与外部 PIT 实现的对比

- WorldQuant Brain / Alphalens 的 `as_of` 模式：本质相同，但他们把时序判断写在策略层；本方案把它沉淀到 schema 层，业务 SQL 更简单
- Quantopian Pipeline `BoundColumn` 的 `latest`/`asof` 语义：本方案的 `tradable_date` 等价于 pipeline 里的"信号生成时刻"，但落地形式是 SQL 字段而非 Python API
